EN Hint · proposed pivot

Explain what I just heard

Stop analysing the whole video up front. Keep manual control of playback, and whenever you pause, explain the last three lines in plain English — the idioms, the words worth knowing, the references — with ten seconds of dialogue behind them as context, so the model reads them the way you heard them.

The new interaction

What you see when you pause

The card no longer dims the video or blocks it — you paused on purpose, so nothing needs to be taken away from you. It sits above the controls and leaves on Esc or on play.

The instant state

“They walked us through the whole architecture…” “…so the whole explanation went over my head, honestly.” “I was completely winging it.”

The lines are already local, so they render on the same frame as the pause. Only the explanations wait on the network.

When there is nothing to say

  • Every word is ordinary. The card says so in one line and closes itself after a moment, rather than inventing difficulty.
  • No captions on the video. There is nothing to explain; the panel already reports this.
  • Paused during an ad. Ignored — ad timelines have nothing to do with cue times.
  • Paused in silence. No cue is playing and none ended in the last ten seconds, so there is nothing to send.

The request

What goes to the model, and what comes back

One small structured call per pause. The strict JSON schema stays — it is what makes the card renderable without guessing.

SENT

// system
The learner is at B1. They paused here because
something was unclear. Explain the idiomatic
expressions, any word a B1 learner would not
know, and any cultural reference they may miss.
Answer in English. Do not translate anything.
Say nothing about words they already know.

// The CONTEXT lines are there so you read the
// TARGET lines correctly. Never explain a term
// that appears only in CONTEXT.
// Captions are auto-generated: they may be
// mis-transcribed. Do not explain a mishearing.

// user
CONTEXT
[410] they walked us through the whole
      architecture in about four slides
TARGET
[411] and honestly?
[412] so the whole explanation went over my
      head.
[413] I was completely winging it.

RETURNED

{
  "items": [
    {
      "term": "go over someone's head",
      "kind": "idiom",
      "meaning": "Too difficult to understand.
                  Said of an explanation."
    },
    {
      "term": "wing it",
      "kind": "phrasal_verb",
      "meaning": "To improvise, unprepared."
    }
  ]
}

The CONTEXT block is every cue that overlaps the ten seconds before the pause, minus the three targets. On a fast talker that is three or four extra lines; on a slow one it is often empty, and the block is omitted entirely.

kind is one of idiom, phrasal_verb, word, slang, reference — it drives the small label on each row. Two fields, no third: there is no translation. An empty items array is a valid, meaningful answer, and the card says so rather than inventing difficulty.

Before you commit to this

Risks and failure modes

acceptedNot every pause is a question

You decided any pause fires it. So the card will appear when you stopped to read a slide or answer the door. The mitigations are that it never blocks the video, it costs about a tenth of a cent, and Esc or pressing play clears it. If it grates in practice, the hotkey‑only trigger is a two‑line change.

latencyYou are now waiting on the network

Today the answer is ready before you need it. From now on there is a visible ~1–2s gap after every pause. The lines render instantly to cover it, but a slow or rate‑limited key will be felt in a way it never was before — and with an immediate trigger, it is felt on every pause, not just the ones you meant.

qualityContext can leak into the answer

The ten‑second window fixes misread idioms, but models are eager to be helpful: asked for context and given it, they will start explaining words from it. The prompt forbids it and the schema cannot enforce it, so the code should drop any returned term that does not appear in the three target lines — the same defensive check clean() does today for cue indices.

dataAuto-captions lie

ASR mishears words, and the model will happily explain a word that was never said. The prompt is told when captions are auto-generated, but this gets more visible when a single line is the whole request.

migrationOld cache goes stale

Existing scan: keys in chrome.storage.local become unreadable by the new code. They should be swept on upgrade, not left to sit.

scopeThe vocabulary list still is not built

The README lists an add-to-vocabulary button as unbuilt. This pivot makes it more valuable, not less — but it stays out of scope unless you say otherwise.

Settled — nothing left open

The order to build it in

Every decision is made. These steps are ordered so the extension keeps working at the end of each one, rather than being broken in the middle.

01

Teach the scheduler to report pauses

Add a pause listener beside the existing rAF loop, guarded on ad-showing and seeking. Nothing else changes yet, so the current behaviour is still intact and the trigger can be verified on its own in the console.

02

Add explain to the service worker

New message type, new prompt with the CONTEXT/TARGET split, new two-field schema, cache keyed on the last cue index. scan stays alive alongside it for now, so both can be compared on the same video.

03

Build the card, wire the pause to it

Cue lookup walking back three cues and then ten seconds; the lines render immediately, the items stream in behind them. The request aborts when you press play. Includes the defensive filter that drops any term absent from the three target lines.

04

Delete the old path

Only once step 3 works: scan, chunkCues, CHUNK_CHARS, MAX_ANNOTATIONS, the mark cursor and consider(), the panel, the two settings, and a sweep of stale scan: keys from chrome.storage.local. The README loses the auto-pause behaviour section and gains this one.

Verified against src/main-world.js, src/content.js, src/background.js, src/scheduler.js, src/options.js and src/overlay.css at the current working tree. Token and cost figures come from CHUNK_CHARS = 12000 and the README’s own estimate of ~3,000 words for a 20‑minute talk.
