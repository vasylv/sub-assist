Getting YouTube subtitles into the extension

This covers only the subtitle pipeline: how the full transcript is read before playback, how the current line is tracked in real time, and how playback is paused while an overlay is up. The OpenAI scan and the vocabulary button are sketched at the end but not designed here.

Two files already exist on disk from the spike: manifest.json and src/main-world.js, plus src/content.js. Everything shown below either comes from those files or is a proposed addition, and each block says which.

1. There is one object that has everything

YouTube builds every watch page from a JSON blob it calls the player response. Buried in it is a list of caption tracks. Each track carries a URL that, with one query parameter added, returns the entire transcript as JSON with millisecond timings. That is the whole trick — the rest of this document is about reliably getting hold of that object.

Picking the right track

A video can have many tracks. kind: "asr" means auto-generated by speech recognition. Prefer a human-written English track, fall back to the auto one.

  • Human tracks have punctuation and casing — much better input for idiom detection.
  • ASR tracks have neither, and split phrases across cues more aggressively.
  • Adding &tlang=en asks YouTube to machine-translate a foreign track. Useful for non-English source video, but the output is translationese — poor material for learning idioms.

Why fmt=json3

Without it you get YouTube's caption XML. With it you get:

  • tStartMs and dDurationMs per event — millisecond precision.
  • A segs[] array, and on ASR tracks each segment carries its own tOffsetMs — i.e. per-word timings, which is exactly what you want to highlight a single expression rather than a whole line.
  • No XML entity decoding to get wrong.

2. The player response arrives by two different routes

This is the part that quietly breaks extensions. YouTube is a single-page app, so "starting a video" means two completely different things depending on how the user got there — and each one delivers the player response by a route the other one's hook cannot see. You have to hook both.

The dedupe matters. Route B can fire more than once for the same video (prefetch on hover, quality changes, ad breaks). Keying on videoDetails.videoId and ignoring repeats is what keeps you from fetching the same transcript three times and re-running the OpenAI scan.

3. Why this code cannot live in a normal content script

A Chrome content script shares the page's DOM but not its JavaScript. It runs in an isolated world with its own window. So a content script reading window.ytInitialPlayerResponse gets undefined, and a content script wrapping window.fetch wraps a copy the page never calls. Both hooks have to run in the page's own world.

What makes it work: "world": "MAIN" at document_start

manifest.json — already on disk. Two content-script entries over the same match pattern, one per world. document_start is not optional: the setter has to be installed before YouTube's inline script assigns.

world: "MAIN" in the manifest needs Chrome 111+. Before that, the only way in was injecting a <script src=chrome.runtime.getURL(...)> tag from a content script — still a valid fallback if you ever need to support older Chromium or Firefox.

4. Following the subtitles in real time

"Real time" has three possible sources, and the choice decides whether you can pause the video before the interesting phrase is spoken or only after. Name the decision now, because everything downstream depends on it.

Recommended

A · Clock-driven from the cue list

Poll video.currentTime against the transcript you already downloaded, and schedule the overlay yourself.

Gives you

  • Lookahead. You know a phrase is 800 ms away, so the overlay is rendered and the pause lands on the right frame.
  • Works with captions turned off — nothing is scraped from the screen.
  • Survives seeking, speed changes, and ad breaks (currentTime is authoritative).

Costs

  • Needs the upfront fetch to have succeeded.
  • You own the alignment; ASR drift is yours to absorb.
Fallback

B · Scrape the caption DOM

A MutationObserver on .ytp-caption-segment, reacting to whatever YouTube renders.

Gives you

  • Perfect alignment with what the viewer literally sees.
  • A safety net when the transcript fetch fails.

Costs

  • Zero lookahead — by the time you see the text, it has been spoken. Pausing then is always late.
  • Requires the user to leave CC on.
  • Depends on YouTube's class names, which are not a contract.
Not available

C · Native TextTrack cue events

The clean HTML5 way: track.addEventListener("cuechange", …).

YouTube does not attach native <track> elements — captions are drawn as ordinary DOM nodes over the player. So there are no cues to listen to. Worth knowing so you don't spend an evening looking for them.

The timing model, concretely

Each annotation the scan produces is anchored to a cue and, where per-word offsets exist, to a character range inside it. That gives three distinct moments per annotation. Playback stops at cue.end — the line is allowed to finish, then the explanation appears; the phrase offset is used only to highlight the words.

Do not drive this off the timeupdate event. It fires roughly four times a second, so a pause can land up to 250 ms late — visibly past the word. Use a requestAnimationFrame loop (~60 Hz while the tab is visible), or, better, compute the next interesting timestamp and setTimeout straight to it, re-arming on seeking, ratechange, play and pause.

Tracking the time precisely enough to stop on it

There are three clocks available, and only one of them is accurate enough to stop the video on a chosen moment rather than somewhere near it.

ClockGranularityWhat it costs you
timeupdate event ~250 ms The browser fires it roughly 4×/sec. A stop can land a quarter-second past the word — audible, and the wrong line is often already on screen. Fine for a progress bar, not for this.
requestAnimationFrame chosen ~16 ms Read video.currentTime every frame. Seeking, playback-rate changes and buffering need no special handling, because the clock is always the truth. Cost is one number comparison per frame. Caveat: rAF is suspended in a hidden tab while YouTube keeps playing audio.
setTimeout to the next mark ~1 ms Arm a timer at (stopAt − currentTime) / playbackRate × 1000. Most efficient and works in a background tab, but you must re-arm on seeked, ratechange, play, pause and — the one people forget — waiting, since the timer keeps running while the video stalls on buffering.
16 ms is already more precision than the data has. json3 cue boundaries are accurate to maybe ±100 ms, and auto-generated tracks drift further than that. rAF is chosen because it is simple and self-correcting, not because it is the most precise option — the extra precision of a timer buys nothing here and costs five edge cases.

The loop, and the three pieces of state around it

src/scheduler.js — written, not yet listed in manifest.json. The interesting parts are the tick loop (one comparison per frame against a cursor, not a scan of every annotation), resync (the only thing a seek invalidates), and the deliberate choice not to clear the fired set when the user rewinds.

The cue lookup that exists today

src/content.js — already on disk. This is the spike version: a binary search over the cue list plus a timeupdate listener, enough to prove the timings line up with the audio. Lines 53–99 are the part that would be replaced by the scheduler described above.

5. Stopping playback while the overlay is up

The mechanism is trivial — document.querySelector("video").pause() on the real element, and YouTube's own UI updates to match, because that is the element its player controls. Everything hard about this is behavioural.

TrapWhat goes wrongHandling
Re-pausing the same phrase The user resumes, the clock crosses the same timestamp again on the next frame, you pause again. The video becomes unplayable. Keep a Set of annotation ids already shown for this video, and only arm each once. Clear it on video change, not on seek.
The user resumes manually They hit space or click play while the overlay is still on screen; the overlay now floats over moving video. Listen for play on the video element and dismiss the overlay from that handler. Treat the video element as the source of truth, not your own flag.
Seeking backwards Rewinding to re-listen re-triggers every annotation in the passage. On seeking, rebuild the schedule from the new time but keep the "already shown" set — the user rewound to hear it, not to be interrupted again.
Pausing during an ad Ads play through the same <video> element with their own timeline, so cue times are meaningless and your overlay appears over the ad. Suspend the scheduler while .ad-showing is present on the player container, and re-arm when it clears.
Too many pauses A dense talk at B1 level can yield an interesting expression every few seconds. Auto-pausing on each is unusable. Rate-limit — at most one auto-pause per N seconds — and/or only auto-pause above a difficulty threshold, leaving the rest as passive highlights. decided
Fullscreen and theater mode An overlay appended to document.body disappears in fullscreen, because the fullscreen element is the player container. Append the overlay inside #movie_player rather than to the body, so it is part of the fullscreened subtree.

Suggested shape

Rather than "pause on hit", model it as a small state machine per annotation: scheduled → prepared → shown → dismissed. The mark is cues[cueIndex].end, so prepared renders the overlay hidden a few hundred milliseconds before the cue ends and the paint is done in time; shown calls pause() and reveals it; dismissed calls play() and marks the id as spent. The user's own play/pause input always wins and forces dismissed.

6. Where the OpenAI scan slots in

Sketch only — the scan itself is the next document. What matters here is that the upfront transcript makes the scan a single background call per video, not a per-cue call during playback. That is the main reason to fetch the whole track up front rather than react line by line.

Key handling. An API key inside a distributed extension is readable by anyone who unpacks it — there is no way around that. For personal use, a key the user pastes into an options page and that lives only in chrome.storage.local is fine. If this is ever shared, the calls have to go through a small backend you own. Worth deciding before the scan code is written, because it changes where the request is made.

7. What can break, and what it looks like

RiskWhyMitigation
High The transcript fetch returns empty or 403 YouTube has been tightening timedtext access — the URL can carry short-lived tokens tied to the session. A request made from the wrong context gets a 200 with an empty body rather than an error. Fetch from the MAIN world (as written) so origin, cookies and Referer match. Treat an empty body as a failure explicitly. Fall back to hooking the player's own /api/timedtext response — the existing code already logs when it sees one, which is the hook point.
Medium Auto-generated captions only No punctuation, no sentence boundaries, phrases split across cues. Idiom detection degrades sharply and "expressions of feeling" are the first thing to be lost. Detect kind === "asr" and tell the model so in the prompt. Consider re-joining cues into sentence-ish windows before scanning, keeping a cue-index map for anchoring.
Medium YouTube changes the internal JSON shape playerCaptionsTracklistRenderer is an internal name with no compatibility promise. Optional-chain every access (already done), and surface a visible "couldn't read captions" state rather than failing silently, so a break is noticed the same day.
Medium Auto-pause is annoying The feature that sounds best in a spec is the one most likely to get the extension switched off. Decided: auto-pause only at or above a difficulty threshold, and at most once per gap. Everything below the threshold is highlighted but never stops the video.
Low No captions, or a live stream Live streams have no complete transcript; some videos have none at all. Already handled as a distinct no-captions signal. Live streams need the incremental /api/timedtext hook or nothing — out of scope for v1.
