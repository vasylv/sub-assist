EN Hint · bug analysis & fix plan

The transcript doesn't follow the video

“my plugin doesn't switch the script if new video is open.” reported 2026-09-03

Open a second video and the extension keeps the first video's subtitles. Pause, and the card explains lines from a video that is no longer on screen. Below: what the code actually does, the one gate that drops the new video on the floor, and a fix in seven small patches.

01 — the mechanism

A transcript has exactly one way in

Both halves of the extension are loaded once, at document_start, and stay alive across YouTube's in-app navigation. So a session is never “started” by a page load — it is started by a caption track list arriving in a player response, and by nothing else.

02 — the failure

YouTube asks about the next video before you go there

YouTube prefetches player responses — for the autoplay-next video, and for thumbnails you hover. Those arrive while the URL still names the video you are watching, so the gate rejects them. That rejection is correct. Throwing the response away is not: when you then navigate, YouTube already has that response cached and never asks the server again.

Confirm it in 20 seconds

The extension already logs every step. Open the console on a watch page, let it autoplay or click through to the next video, and watch for [en-hint] track: … followed by [en-hint] N cues via …. If neither line prints for the new video, the diagnosis above is confirmed — the player response never reached handlePlayerResponse with a matching URL. A [en-hint] caption response seen via fetch line with no track: line after it is the same signal.

03 — the proposal

Park what arrives early, and notice the navigation

Four moves, in two layers. The page world stops destroying evidence and gains a way to act on a navigation. The isolated world stops trusting that silence means nothing changed.

Park, don't drop

A response whose URL never settles goes into parkedByVideo instead of being discarded. It is the only copy; keep it.

Watch for the navigation

On yt-navigate-finish plus a 500 ms poll backstop: clear the session, replay the parked response for the new video, or re-post a transcript already built for it.

Reset on navigation, not on a message

content.js clears its own cues the moment the URL changes. Even if the page world stays silent forever, the wrong lines can never be sent.

Guard both ends

onTranscript gets the URL check its siblings already have, and explainAt refuses to send when videoId no longer matches the URL.

Seven focused patches

Each block below is a real excerpt of the file as it stands today against the proposed replacement. Nothing outside these regions changes.

Page world — src/main-world.js

Patch 1 lines 23–35 Split the one overloaded slot into a session id, an in-flight set, and two bounded caches.

05 — before you say yes

Risks and open questions

RiskA navigation during provokeDownload restores captions on the wrong video
provokeDownload can hold the player for up to 27 s (15 s waiting for #movie_player, then 3 × 4 s of asking). Its finally block unconditionally restores the viewer's previous caption track — on whatever video is on screen by then. That is already true today, but starting sessions on navigation makes it far more likely. The proposed guard is one line in the finally: if (watchedVideoId() !== videoId) return; before the restore. Not included in the seven patches above — say the word and I'll add it.
QuestionDoes yt-navigate-finish still fire?
It is YouTube's own event and not a public API, so it can be renamed without notice. That is why every patch pairs it with a 500 ms location poll — the poll alone is enough, the event just makes the switch feel instant. If you would rather not add a second interval timer (scheduler.js already runs one at 2 s), I can fold the check into that existing loop instead.
NoteMemory is now bounded — it was not before
capturedByVideo grows for every video whose track the player downloads and is never trimmed. The two new maps use a shared remember() helper capped at 12 entries. Applying the same helper to capturedByVideo is a one-line change included in Patch 1's spirit but not in its diff — flag it if you want it.
BonusGoing back to a video becomes instant
transcriptByVideo means returning to a video you already watched re-posts its transcript immediately, with no second round of provoking the player into re-downloading the track. This is not required to fix the reported bug — it falls out of having a navigation watcher at all.
